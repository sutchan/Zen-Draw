## 2. O1 繁体中文语言支持补齐（P2）

- **问题背景**：当前仅 `zh`/`en` 两种语言（`draw-types.ts L35`），110 个翻译键。项目的多语言规划为「简中（默认）→ 繁中 → 英文」，繁中缺失导致繁体用户只能使用简体或英文界面。
- **实施方案**：① `types.ts` 保持 `TranslationKey` union 不变，新增 `locales/zh-Hant.ts` 完整翻译 110 键（台湾用语习惯：設定/搜尋/網格/檔案/複製/匯入）；② `Language` union 扩展为 `"zh" | "zh-Hant" | "en"`，`createTranslator` 回退链「繁中缺键回退简中、英文缺键回退简中」；③ 外观 Tab 与 HeaderBar 语言切换 UI 增加繁中项；④ `html lang` 取 `zh-Hant`。
- **预期效果**：繁体用户可直接使用母语界面；键完整性仍由编译期 `Record<TranslationKey, string>` 保证，无需新增测试即可覆盖 110 键 × 3 语言的一致性。
- **优先级**：P2（用户价值明确、实施成本低、风险小）。

## 3. O2 Node 版本策略统一（P2）

- **问题背景**：三处 Node 版本约束不一致——CI（`ci.yml` 两处 `node-version: 22`）、本机开发环境（Node 26，`.nvmdrc` 内容 `26.13.1`）、`package.json` 无 `engines` 字段。开发者按 `.nvmdrc` 用 Node 26 时，CI 在 22 上验证，行为差异（如 v5.7.13 前的 localStorage 测试失败）已经造成过排查成本。
- **实施方案**：① `package.json` 增加 `"engines": { "node": ">=22" }`；② 将 `.nvmdrc` 内容与 CI 对齐（Node 22），或统一改为标准 `.nvmrc`；③ `ci.yml` 读取版本文件作为单一来源，避免两处硬编码；④ `deployment.md` 同步说明。
- **预期效果**：开发/CI/文档三处版本一致，消除「本机通过、CI 失败」（或反之）的环境差异类问题；新成员环境搭建时间减少。
- **优先级**：P2（成本低、可消除一类复发问题）。

## 4. O3 端到端测试补齐（P2）

- **问题背景**：当前质量保障为 7 个测试文件 69 个单元/组件用例，**无 E2E 测试**。「点击抽取 → 滚动 → 结果 → 历史 → 复制」这条核心用户路径没有端到端回归保障，跨组件协作回归（如快捷键状态分流、aria-live 播报）只能靠人工冒烟。
- **实施方案**：① 引入 Playwright（`@playwright/test`），配置 Chromium + Firefox 两引擎（对齐「最新 2 个主要版本」浏览器支持目标）；② 首批覆盖 3 条主路径：数字抽取全流程（含 Space 快捷键分流）、名单抽取与导出、设置持久化（刷新后保持）；③ CI 增加 e2e job（依赖 quality-check 通过）；④ 测试选择器复用既有语义化 id（`draw-area`、`app-footer-version` 等，零额外改造）。
- **预期效果**：核心路径回归自动化；语义化 id 已具备，预计新增 10–15 个 E2E 用例即可覆盖主路径（具体以编写结果为准）。
- **优先级**：P2（收益最高的质量短板）。

## 5. O4 安全审计门禁收紧（P3）

- **问题背景**：`security-check` job 中 `npm audit --audit-level=high` 带 `continue-on-error: true`，audit 失败不阻塞合并，形同虚设；依赖漏洞只有 high 级别门槛且无人工复审记录。
- **实施方案**：① 将 `npm audit` 结果改为产出报告 artifact 并在 PR 评论中展示（保留 continue-on-error 但强制可见）；② 或改为白名单机制：已知可接受的上游漏洞显式登记并注明理由，未登记的 high+ 漏洞阻塞合并；③ `dependency-review` 保持仅 PR 触发。
- **预期效果**：漏洞可见性从「静默失败」变为「PR 内强制可见」；误报可通过白名单治理而非全局放行。
- **优先级**：P3（当前依赖树审计通过，属预防性改进）。

## 6. O5 抽取滚动动画渲染优化（P3，需实测）

- **问题背景**：滚动动画以 `setInterval` 每 80ms dispatch `UPDATE_ROLLING` 更新 React 状态，每次 tick 触发依赖 `results` 的组件树重渲染；`LIMITS.MAX_COUNT = 1000` 时单次 tick 重渲染最多 1000 个数字节点。**当前无性能实测数据**，可能无感知问题，也可能在低端设备出现掉帧。
- **实施方案**：① 先用 React Profiler / Chrome Performance 对 count=1 与 count=1000 两档做基线测量（帧率、单 tick commit 时长），**无实测数据不做改造**；② 若确认超阈值，备选方案 A：滚动期间以 `requestAnimationFrame` 驱动并直接写 DOM 文本（绕过 React 渲染），结束时一次性 dispatch 终值；备选方案 B：滚动态子组件用 `React.memo` + 仅文本 diff 隔离重渲染。
- **预期效果**：以实测基线为准；若实施，预期滚动期 commit 时长下降、低端设备帧率提升（量化指标待测量后补充到本节）。
- **优先级**：P3（先测量后决策；count=1 的默认场景大概率无感）。

## 7. O6 历史记录批量导出（P3）

- **问题背景**：历史记录（≤100 条）仅支持单条点击复制，无批量导出；用户不能离线留存抽取记录（名单有导出、历史没有，能力不对称）。
- **实施方案**：① 历史区增加「导出」按钮，生成 CSV（`timestamp,results`）与 JSON 两种格式，前端 Blob 下载；② 文件名含日期与页脚 build 编号；③ 导出按钮带语义化 id（如 `history-export`）并纳入无障碍标签。
- **预期效果**：补齐数据留存能力；实施成本约 1 个组件 + 1 个纯函数（可测试）。
- **优先级**：P3。

## 8. O7 历史列表虚拟化预案（P3，条件触发）

- **问题背景**：历史列表当前 `history.map` 全量渲染（`history-list/index.tsx`），无虚拟化/分页；但条数硬上限 100 条且容器 `max-h-[60vh] overflow-y-auto`，**当前规模无性能风险**。
- **实施方案（预案，不立即执行）**：仅当未来放宽历史上限（如 ≥1000 条）或增加历史详情时，引入 `@tanstack/react-virtual` 做窗口化渲染；在此之前保持简单实现。
- **预期效果**：当前零收益零风险；预案避免未来扩容时临时调研。
- **优先级**：P3（条件触发型，当前不实施）。

## 9. O8 PWA 离线支持（P3）

- **问题背景**：纯客户端、无后端依赖，天然适合 PWA；当前断网即白屏，无法离线使用。
- **实施方案**：引入 `@serwist/next`（Next.js App Router 成熟方案）：① Service Worker 预缓存构建产物 + 运行时缓存兜底；② `manifest.json` 图标与主题色对齐 11 套配色；③ 安装成功后 `deployment.md`/README 更新部署说明；④ 注意隐私边界：仅缓存同源静态资源，无网络请求场景本就存在。
- **预期效果**：可安装到桌面/手机、离线可用；Lighthouse PWA 审计项补齐（分值以实施后实测为准）。
- **优先级**：P3（体验增强，非当前痛点）。
